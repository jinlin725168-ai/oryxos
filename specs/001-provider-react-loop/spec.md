## User Scenarios & Testing *(mandatory)*

### User Story 1 - 一次对话内自动调用工具完成任务 (Priority: P1)

用户在命令行里向 Agent 提出一个需要外部信息才能回答的问题（例如"查一下北京天气，告诉我今天穿什么"）。
Agent 自己判断出需要获取外部信息、调用相应工具拿到结果，再综合结果给出最终回答——整个过程用户
只发了一句话，不需要手动执行任何工具或中间步骤。

**Why this priority**: 这是本特性的核心价值，也是 OryxOS 区别于普通问答机器人的根本——Agent 能
"自己想、自己动手"。只要这一条跑通，就已经是一个可演示、有价值的最小闭环（MVP）。

**Independent Test**: 启动交互对话，输入一个需要实时外部信息的问题，观察 Agent 在无人工干预下
自动获取信息并给出综合回答，即可独立验证。

**Acceptance Scenarios**:

1. **Given** 已启动交互对话且已配置好可用的大模型与一个天气查询工具，**When** 用户输入
   "查一下北京天气并告诉我今天穿什么"，**Then** Agent 自动获取当日天气并返回结合天气的穿衣建议，
   期间用户未手动触发任何工具。
2. **Given** 同上，**When** 用户提出一个无需任何外部工具即可回答的问题（如"用一句话解释什么是 ReAct"），
   **Then** Agent 直接作答，不调用任何工具。
3. **Given** 某个任务需要连续两次工具调用才能完成，**When** 用户提出该任务，**Then** Agent 依次
   完成多次"调用→拿到结果→继续推理"后给出最终回答。

---

### User Story 2 - 多轮对话与上下文延续 (Priority: P2)

用户在同一次对话中连续追问，Agent 记得前面聊过的内容，后续回答能正确引用先前轮次的信息。

**Why this priority**: 多轮上下文是"对话"而非"一问一答"的前提，显著提升可用性；但在单轮工具闭环
（P1）之上才有意义，故次之。

**Independent Test**: 先问一个问题得到回答，再追问一个依赖上一轮结果的问题，验证 Agent 是否
正确沿用上下文而无需用户重复背景。

**Acceptance Scenarios**:

1. **Given** 用户已在本次对话中问过"北京天气如何"并得到回答，**When** 用户追问"那适合穿什么"，
   **Then** Agent 基于上一轮的天气结果作答，无需用户再次说明是哪座城市。
2. **Given** 一次很长的对话已超出可容纳的上下文长度，**When** 用户继续对话，**Then** 系统保留近期
   对话、丢弃最早部分，对话仍能继续进行而不报错。

---

### User Story 3 - 模型无关（更换大模型不改变对话行为） (Priority: P3)

运维/开发者把底层对接的大模型从一家供应商切换到另一家（或换一个模型），`oryxos chat` 的多轮对话
与工具调用行为保持不变，使用者无感知。

**Why this priority**: 这是 OryxOS "不锁厂商"的关键属性，对企业很重要；但它是一种可移植性保障，
在核心对话闭环之上验证，故列 P3。

**Independent Test**: 把同一段对话脚本分别在两个不同大模型供应商下运行，比较是否都能完成相同的
工具调用与得到符合预期的回答。

**Acceptance Scenarios**:

1. **Given** 系统已配置至少两个不同的大模型供应商，**When** 分别用其中任一供应商运行同一段查天气
   对话，**Then** 两者都能自动完成工具调用并给出合理回答，对话方无需改动任何用法。

---

### Edge Cases

- **模型反复要求调工具、不收敛**：达到配置的迭代上限（默认 10 轮）时强制结束，返回当前可给出的
  最佳回答或明确说明未能完成，绝不无限循环。
- **工具执行失败**（如天气服务超时/返回错误）：把失败信息回填进推理，Agent 据此调整（换措辞、
  如实告知用户"暂时拿不到天气"），而非整体崩溃。
- **工具越界**：工具的外部访问超出安全边界（如请求了不在白名单内的域名）时被拒绝，并把拒绝原因
  如实反馈到推理中。
- **大模型调用失败**：给用户清晰的错误提示；核心阶段不做自动故障切换。
- **用户问题与任何工具无关**：Agent 直接回答，不产生任何工具调用。
- **凭证缺失/非法**：启动或首次调用时给出清晰报错，指明缺少哪个凭证，而非静默失败。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持通过交互式命令行进行多轮对话——用户发送一条消息、得到一条回复，并可
  继续追问。
- **FR-002**: 当回答用户需要外部信息或操作时，系统 MUST 能自主判断并调用相应工具（如查询天气），
  无需用户手动触发。
- **FR-003**: 系统 MUST 在工具执行后把结果回填到推理过程继续推理，可在一次对话内连续多次调用工具，
  直到形成最终回答。
- **FR-004**: 系统 MUST 设有工具调用的迭代上限（默认 10 轮），达到上限时强制结束并返回当前可给出的
  回答，避免无限循环。
- **FR-005**: 当用户问题无需外部工具即可回答时，系统 MUST 直接作答，不进行任何工具调用。
- **FR-006**: 系统 MUST 在同一次对话内保留上下文，后续消息可引用先前轮次的信息；上下文超出容纳
  上限时 MUST 保留近期对话、丢弃最早部分。
- **FR-007**: 系统 MUST 让底层大模型可替换——更换所对接的大模型供应商或模型 MUST NOT 改变上述
  对话与工具调用行为，使用者无感知。
- **FR-008**: 当工具执行失败时，系统 MUST 把失败信息纳入推理供 Agent 调整或如实告知用户，MUST NOT
  因单次工具失败而中断整个对话。
- **FR-009**: 当大模型调用失败时，系统 MUST 给出清晰的错误反馈（核心阶段不做自动故障切换）。
- **FR-010**: 工具的外部访问 MUST 受安全边界约束（如域名白名单），越界请求 MUST 被拒绝并把原因
  如实反馈。
- **FR-011**: 系统 MUST 通过**结构化日志**记录每一次大模型调用（provider、模型、token 用量、耗时）
  与每一次工具调用（工具名、成功/失败、耗时），成功与失败都记录，且 MUST NOT 在记录中出现明文
  凭证等敏感信息。（SQLite 审计表 `tool_invocations` / `llm_calls` 的落库在引入存储的后续特性兑现）
- **FR-012**: 敏感凭证（大模型访问密钥等）MUST 经环境变量提供，MUST NOT 明文写入配置或出现在对话/
  日志中。

### Key Entities *(include if feature involves data)*

- **对话（Session）**：一次交互的上下文容器，按用户与 Agent 归属，包含按时间累积的消息历史。
- **消息（Message）**：对话中的一条记录，来源为用户输入、模型输出或工具结果之一。
- **工具（Tool）**：可被 Agent 调用的外部能力；本特性至少包含一个用于获取外部信息的工具（以天气
  查询作为验收示例）。
- **大模型供应商（Provider）**：被对接的大模型服务的抽象，可在不改变对话行为的前提下替换。
- **调用记录（Invocation Record）**：每次模型调用或工具调用的留痕（含是否成功、耗时等），供审计。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户在一次对话中提出需要实时外部信息的问题时，无需手动执行任何工具，即可得到一个
  综合了该实时信息的完整回答。
- **SC-002**: 对于需要工具协助的任务，Agent 在单次对话内自动完成"判断→调用→回填→作答"闭环，
  全程无需人工介入中间步骤。
- **SC-003**: 在同一对话中连续追问时，Agent 能正确引用上一轮的信息，用户无需重复背景。
- **SC-004**: 同一段查天气对话脚本在 DeepSeek 与 智谱（Zhipu GLM）两个供应商下都能跑通，并各自
  得到符合预期的工具调用与回答。
- **SC-005**: 当工具或大模型不可用时，用户 100% 收到明确的说明，而不是无响应、卡死或崩溃。
- **SC-006**: 任何对话都会在有限轮次内结束——不存在因反复调用工具而无限循环的情况。

## Assumptions

- 本特性面向开发者/运维通过**命令行交互**使用；企业 IM 等其他接入渠道不在本特性范围（属后续阶段）。
- 对话历史在本特性中于**运行进程内保持**即可；跨进程重启的持久化属后续特性（存储/Web Service 阶段）。
- 审计信息在本特性以**结构化日志**记录；SQLite 审计表（`tool_invocations` / `llm_calls`）在引入
  存储的后续特性统一落库。
- 本特性至少提供**一个用于获取外部信息的工具**：一个查询天气的 HTTP 工具，连接**免注册 key 的
  公开天气 API**（如 open-meteo.com），其域名列入 HTTP 白名单；验收判定"是否成功获取并综合了天气"，
  不锁死具体温度数值。完整内置工具集与插件式扩展属后续特性（Tool 体系阶段）。
- 用于验收的大模型供应商为 **DeepSeek** 与 **智谱（Zhipu GLM）** 两家；两者均兼容 OpenAI 协议，
  通过在两者间切换来验证"模型无关"。
- 工具调用迭代上限默认 **10 轮**，可按对话配置调整。
- 运行需要有效的大模型访问凭证（经环境变量提供）与一个可访问的外部信息来源（如公开天气数据服务）。
- 核心阶段**不做**大模型/工具的自动故障切换与流式输出；这些属扩展阶段。
